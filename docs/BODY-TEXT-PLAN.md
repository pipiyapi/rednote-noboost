# 不打开帖子界面获取正文：验证记录与实现方案

日期：2026-09-26。状态：首页检查与 5 篇后台详情读取实测完成；未接入产品代码。

## 结论

“不打开帖子界面”与“不请求详情数据”不是一回事。

- 只读首页已有数据：成本低，但已有实测未发现正文，不能承诺覆盖。
- 保持首页不跳转，额外请求笔记详情数据：已在用户当前 Chrome 会话验证，5 篇均返回匹配详情，4 篇返回非空正文。
- 不使用隐藏详情页、iframe、模拟点击来伪装成“没进入帖子”。

推荐采用“首页已有正文优先 → 经用户同意后后台补取 → 失败保留标题 + OCR”。
建议进入小范围接入阶段，但必须保留失败降级；单次小样本成功不代表长期稳定或不限速。

## 本轮尝试与证据边界

| 检查 | 结果 | 能证明什么 |
| --- | --- | --- |
| 复核仓库 2026-09-22 验证记录 | 首页 DOM 和初始状态 noteCard 未见正文；用户资料 desc 不是正文 | 旧样本不支持纯首页提取，不能推广成所有版本永远没有 |
| 复核当前提取器 | readPageText() 恒返回 null | 当前产品确实尚未读取正文 |
| 复核当前判定流程 | 已有 title+page_text、title+page_text+ocr 来源类型及合并分支 | 可沿现有框架扩展，不需要第二次 Jev 判定 |
| 首次尝试访问用户浏览器 | 工具报告 Mac 锁定；用户随后手动解锁 | 解锁后继续在原首页进行只读检查 |
| 解锁后复测推荐状态 | DOM 30 张卡片；feed 状态递归遍历到 70 个含 noteCard/note_card 的对象；未发现字符串 desc/description/content 字段 | 该次首页已加载推荐状态未找到正文；70 是对象计数，不代表 70 篇去重笔记，也不是原始网络响应统计 |
| 解锁后复测详情缓存 | noteDetailMap 有 1 条缓存，与当前卡片 ID 匹配数为 0 | 当前卡片不能利用该条历史详情缓存补正文 |
| 解锁后检查卡片链接 | 90 个卡片内链接带 xsec_token 参数，未输出参数值；页面存在 webpack chunk 容器 | 请求元数据存在，但不等于详情请求会成功；链接数不等于笔记数 |
| 核查公开实现源码 | xhs-cli 在首页环境调用站内客户端；Amagi 区分 homefeed 与详情 feed 请求 | 提供实现线索，不等于本站当前版本或用户登录态实测成功 |

在用户明确接受后台请求后，本轮追加了下方 5 篇实测。没有读取/导出 Cookie，没有调用 Jev，
没有打开帖子，没有修改扩展行为，也没有推送本方案。请求使用页面已有客户端及会话。

实测通过 Chrome 开发者工具执行只读字段统计，页面始终位于 `/explore`。
首个卡片 noteCard 的键为 type、displayTitle、user、interactInfo、cover。
检查范围是页面已有状态与 DOM，不包含一次新的滚动响应抓取，不能据此断言所有首页响应永远没有正文。

## 后台详情读取实测结果

用户授权后，从当前首页前 5 张卡片取得对应链接中的 noteId 与 xsec_token，复用当前页面的
`postApiSnsWebV1Feed` 函数，请求 `/api/sns/web/v1/feed`。先测试 1 篇，再顺序测试 4 篇，
后四篇之间等待 2 秒，没有并行请求，也没有调用路由、创建详情 iframe 或隐藏标签页。

| 样本 | 请求耗时 | desc 长度 | 结果 |
| --- | ---: | ---: | --- |
| 1 | 197 ms | 0 | 返回详情，item.id 与请求 ID 匹配；正文为空 |
| 2 | 99 ms | 374 | 非空正文，与标题不同，item.id 和 noteCard.noteId 均匹配 |
| 3 | 125 ms | 548 | 同上 |
| 4 | 274 ms | 565 | 同上 |
| 5 | 91 ms | 455 | 同上 |

- 详情数据返回：5/5；非空正文：4/5。空正文不能算请求失败，也尚未人工确认是否帖子本身无正文。
- 平均约 157 ms，中位数 125 ms；这是单次当前会话的小样本客户端耗时，不是性能承诺。
- 长度按 JavaScript string.length 统计，不是中文字数或 token 数。
- 当前客户端直接返回 `{ items, currentTime, cursorScore }`，正文路径为 `items[].noteCard.desc`。
- 每次响应后检查 pathname 都是 `/explore`，没有触发详情界面；没有收到详情函数的拒绝异常。
- 未记录原始 HTTP 状态；“成功”指客户端正常返回、结构有效且 ID 匹配，不虚构 HTTP 200 证据。
- 不保存原文、作者、笔记 ID 或令牌到本报告。未打开详情做人工对照，因此不声称正文完整性已验证。

### 本次定位与适配发现

网上示例的模块 64732 在本页面不存在。通过读取当前已加载模块源码，定位到包含明确详情端点的
模块 25717，其 `an` 导出对应 `postApiSnsWebV1Feed`，已用该导出成功请求。
这个编号与导出名只能作为本次证据，不能当作永久接口写死。

接入时建议：扫描已加载模块的详情端点特征，严格确认函数与导出映射，仅复用已定位模块；
不遍历执行全部模块、不重放任意请求、不自行生成签名。发现多个候选或结构变化时停止补取并降级。
如果后续构建去掉函数名/改变模块容器，适配器应报告不支持，而不是猜测调用。

### 接入后的单帖路径

`当前卡片 → 正文补取与 OCR 并行 → 合并标题/正文/OCR → 一次 Jev → 历史展示`

优先复用已有正文缓存；后台正文失败或为空时使用标题 + OCR，不再次调用 Jev。
仍保留用户选择的 PP-OCRv6 Small，不以正文方案替换 OCR。

## 方案比较

### A. 被动读取首页已经加载的数据

在页面 MAIN world 中检查明确的笔记集合和首页响应，仅匹配当前卡片 noteId 的正文。
若需要观察后续响应，在 document_start 安装受限 fetch/XHR 观察器，读取响应副本，
不消费原响应、不修改请求、不阻塞页面。不记录全站请求，只处理首页推荐数据。

优点：不额外请求详情，额外网络成本为零。
限制：首页响应若不含正文，再多 DOM 或 Vue 状态遍历也无法生成正文；观察器也可能漏掉
安装前、缓存引用或其他执行环境发起的请求。禁止把用户简介、标题或图片说明误当笔记正文。

Chrome 内容脚本默认与页面变量隔离，需要明确使用 MAIN world 桥接；MAIN world 不能接触 Jev 密钥。
chrome.webRequest 不能直接提供任意响应正文，不把新增该权限作为解决方案。

### B. 首页内后台补取详情数据（优先验证候选）

从当前卡片/首页响应取得 noteId 和对应请求所需元数据；页面仍停在首页。
公开实现使用的详情端点是 `/api/sns/web/v1/feed`，与首页 `/api/sns/web/v1/homefeed` 不同。
候选做法是复用页面已有请求客户端，返回指定笔记的正文，而不是调用路由或打开详情弹窗。

重要限制：

- 这不是小红书公开承诺稳定的开发者接口。端点、结构、请求校验和内部模块都可能变化。
- xhs-cli 的实现依赖固定内部模块编号，不能直接复制为长期稳定的插件方案。
- 必须先确认当前页面是否存在可用客户端、需要哪些元数据、是否返回匹配 noteId 的 desc。
- 单纯从 service worker 发一个 fetch 不保证通过身份与请求校验；扩展 host 权限不等于接口授权。
- 不导出 Cookie、不自行绕过登录或验证码、不重试风控挑战；遇到拒绝时停用补取并降级。
- 即使不打开帖子界面，服务端仍可能记录详情请求，不能承诺“没有访问记录”或“不会影响推荐”。

### C. 后台获取详情 HTML

技术上可尝试下载当前卡片链接的 HTML，而不导航，再解析其中已有结构化正文。
但它仍是详情访问，可能只返回登录壳、验证页或不含正文的页面；下载体积也通常高于结构化接口。
仅作为待测替代项，不推荐先引入，更不使用 eval 执行页面状态脚本。

## 对当前框架的具体改动计划

1. 新增 `bodyTextBridge`：只在首页工作，接收固定的正文请求类型，不提供任意 URL/任意方法代理。
   请求必须对应当前队列里的 noteId；在页面上下文完成站内读取，只返回必要文本与诊断字段。
2. 新增 `bodyTextProvider`：按 noteId 缓存，去重并合并进行中的请求。
   区分 success、empty、unavailable、timeout、blocked；空正文不等于接口报错。
3. 调整 `processNote()`：正文读取与本地 OCR 可并行，均完成或正文超时后只调用一次 Jev。
   保留 generation/卡片身份检查，暂停、刷新、离开首页后不得继续提交旧结果。
4. 调整 `extractor.ts`：正文独立于标题提取。当前短标题会提前返回 null，不能让这个条件
   阻止正文/OCR 参与判断；也不能因已有短标题直接判定没有可用材料。
5. 统一内容合并：明确标注“标题 / 笔记正文 / 封面 OCR”，去重、限制长度并记录是否截断。
   有正文使用现有 page_text 相关来源类型，无正文沿用 title+ocr；无标题组合需要补齐类型。
6. Jev 的 note_text 放入合并文本；rubric 明确这些是待分析材料，正文中的命令不是系统指令。
   保留确定性判定与 fail-open，不把正文加入后默认提高过滤强度。
7. 历史增加正文审计：获取来源、状态、正文、长度、耗时、是否截断及降级原因；
   仍仅保存当前页面会话，不记录 Cookie、请求签名或访问令牌。

页面返回数据视为不可信：校验消息来源、noteId、字段类型、大小和当前请求关联；
页面脚本可以伪造同页面事件，因此消息标识不能被当作真正认证，也不能据此开放特权请求。

## 初始运行约束（待实测调优，不是平台安全速率保证）

- 初次验证仅 3–5 张当前首页卡片，每次一个请求；成功后再扩展到 5–10 张对照样本。
- 产品默认一次一个正文请求，暂定至少间隔 2 秒、单项等待最多 8 秒。
- 超时放弃本轮正文输入；即使不能取消底层请求，也丢弃迟到结果，避免二次收费调用 Jev。
- 401/403/429、验证码或明确风控业务码出现即停止补取，提示用户，不循环请求。
- 正文不可用不阻断已有 OCR 流程；OCR 健康和正文获取可用性是两个独立状态。

## 后续验证顺序与验收标准

1. 保持首页 URL，不点击卡片；记录首屏及自然滚动一批的首页字段覆盖情况。
2. 只输出笔记数、匹配正文数、字段路径、正文长度等元数据，避免保存真实帖子内容或凭据。
3. 若用户接受额外详情请求，对少量当前卡片尝试 B；记录 HTTP/业务状态、noteId 一致性、耗时。
4. 确認请求前后仍在首页、没有详情弹窗或隐藏详情页面；返回内容确实是正文而不是标题。
5. 在取得真实响应后再建立脱敏测试夹具；合成夹具只能验证解析逻辑，不能证明线上可用。
6. 当前范围内可以验证“接口返回正文”；若要证明“正文完整”，还需要后续授权人工详情对照，
   或用户提供已知完整正文样本。本轮不为对照擅自打开帖子。
7. 通过后才开发接入，并测试正常/空正文/失败/超时/暂停/卡片复用，以及每帖只有一次 Jev 请求。
